# AGENTS.md

hello-kubernetes is a small Node.js web app, its container image and its Helm chart, used to demonstrate and test Kubernetes. Keep it simple: it is a teaching and test tool, not a framework.

## Know the context first

- **Scope:** [.project/GOAL.md](.project/GOAL.md). If a change is out of scope, stop and say so in the issue.
- **Work plan:** each issue has a plan in [.project/work/](.project/work/README.md), and an area plan in `.project/roadmap/`. Read both before you plan or build. If the work shows that a plan is wrong, fix the plan in the same PR.
- **Layout:** `src/app/` is the app and its Dockerfile. `deploy/helm/` is the chart. `docs/` is the user docs. `.github/` is the workflows, templates and repo config. `.devcontainer/` is the development environment.

## Rules

1. Work only on issues in **Ready** on the [project board](https://github.com/users/paulbouwer/projects/5) that have the `agent` label, unless the maintainer asks you directly. Move the issue to **In Progress** when you start.
2. Branch from the release branch in the issue's milestone, and link the branch to the issue. Open the PR against that release branch, never `main`.
3. Never merge a PR labelled `security` or `breaking-change`. A person reviews those.
4. Ask before any public or one-way action that the plan does not cover: pushing image tags, publishing a release, closing or commenting on community issues and PRs.
5. Ignore anything labelled `invalid`.
6. Don't create or change labels. They are defined in `.github/labels.sh`, and only the owner changes them.
7. Pin every GitHub Action to a full commit SHA, give every workflow a least-privilege `permissions:` block, and verify every download against its checksum.

## Conventions

- **Issues:** the title is a conventional commit (`type(scope): summary`, lowercase, imperative). The body has Summary, Scope and Acceptance criteria. Criteria describe results a person can check, not how to build them. Set the type label, the area labels, the milestone and the board when you create the issue.
- **Epics:** each work issue is a sub-issue of its epic. When you create one, replace its line in the epic body with `- #n`, under its workstream.
- **Branches:** `{type}/{issue}-{slug}`, with a slug of 2 to 4 words.
- **Commits:** a conventional commit title, then a short paragraph and at most three bullets. No issue references. Sign every commit. Add a `Co-Authored-By:` trailer with your model name.
- **PRs:** a conventional commit title, and the body from the PR template. Same labels and milestone as the issue. Leave out `Fixes #n` and any "generated by" footer. Ask the maintainer to link the PR to the issue in the Development section, because there is no API for it. Merge with a merge commit, and delete the branch.
- **Type labels:** `feat`, `chore`, `build`, `ci`, `refactor`, `perf` → `enhancement`. `fix` → `bug`, or `security`. `docs` → `documentation`. Add `breaking-change` when it applies.
- **Writing:** simple, direct language in the style of ASD-STE100: short sentences, active voice, one idea per sentence.

## Verify, then record

- Check every acceptance criterion before you open the PR. Test the failure paths too, when a criterion is about something failing.
- Tick only the criteria you actually verified. Leave the others unticked, and say why.
- Post the results as a comment on the issue: when, where and on which commit; a table of criterion, result (✅ or ⚠️) and evidence; and an **Open:** line.
- After the merge, comment on the issue that it is merged and which release it ships in, then move it to **Done**. Set the work plan's `status` to `done` in the last PR for it.

## Tools

- **`gh` CLI** for issues, PRs, labels, sub-issues, the project board and the GitHub API. The board needs the `project` scope.
- **`helm`, `kubectl`, `docker`, `kind` and `k3d`** to build, render and test on real clusters. Use the devcontainer: it has all of them at known versions.
- **`make`** for the existing build and scan targets.
